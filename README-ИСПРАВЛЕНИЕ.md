## Что положить в Assets

Кидать `.onnx` можно с любым именем — приложение само найдёт. Рекомендуемый экспорт
(из обычного venv с ultralytics):

```
pip install ultralytics
yolo export model=yolov8n.pt format=onnx imgsz=640
```

Получившийся `yolov8n.onnx` → в `Detector\Assets\`. YOLOv5n тоже поддержан
(`format=onnx` из yolov5 даёт `[1,25200,85]`). Если экспорт делать с `nms=True`
(ultralytics), придёт `[1,300,6]` — этот вариант декодер тоже понимает, NMS в этом
случае просто не с чем работать. Старый `TinyYolo2_model.onnx` больше не поддерживается
намеренно: в логе будет прямое сообщение об этом вместо мусора.

## Обновление 5: фикс паузы и ASCII-сплэш

**Баг «после паузы Play не продолжает, всё висит»**
- Причина: `FramePump.Play()` при `_isPlaying==true` делал пустой `return` — а после
  `Pause()` прогон формально ещё «играл» (флаг `_isPaused=true`). Повторное нажатие
  Play ничего не делало, помп оставался в паузе. ПлюсStop на паузе оставлял
  `_isPaused` взведённым — следующий прогон «зависал» с самого начала.
- Исправлено: `Play()` на уже играющем источнике теперь **снимает паузу**; при старте
  нового прогона `_isPaused` гарантированно сбрасывается; `Pause()` вхолостую (когда
  ничего не играет) больше не взводит флаг.
- В `MainViewModel.PlayAsync` добавлена логика: Play по тому же файлу = resume;
  Play по другому файлу = корректная остановка старого прогона и старт нового.

**Сплэш при запуске (`Views/SplashWindow`)**
- `StartupUri` в App.xaml убран; `App.OnStartup` показывает сплэш, он сам открывает
  MainWindow.

## Обновление 6: экспорт без стопора + выбор кадров + сплэш-косметика

**Баг «экспорт кадров ничего не делает, приложение стопорится» (на паузе и после конца видео)**

  `FramePump.Stop()` (вызывается перед экспортом) блокировал UI-поток ожиданием помп-таска.
  Если помп в этот момент был посреди кадра — взаимное ожидание: UI ждёт помп, помп ждёт UI
  (отсюда «стопор» до 5 с и ощущение зависания; при остановке на паузе — гарантированно).
- Исправлено: все UI-апдейты из помп-потока идут через `BeginInvoke` со снапшотами
  (список детекций, счётчик треков, индекс кадра передаются значениями) — помп никогда
  не ждёт UI-поток. Экспорт-щит `_isExporting` ставится до диалога папки (двойной клик
  больше не открывает второе окно).
- Экспорт теперь **виден**: строка статуса `export 250/1840 · saved 63`, обновление

## Обновление 7: стопор «пауза→Stop» и «экспорт на летящем видео»

**Симптом**: на паузе нажать Stop — виснет; экспорт кадров во время проигрывания — виснет;
после естественного конца видео всё работает.

**Корень**: тот же класс дедлока, что чинился в Обновлении 6, но по другому ребру:
- `FramePump.Stop()` синхронно ждал помп-таск на UI-потоке (`_pumpTask.Wait(5000)`);
- поток помпы на выходе (pause-loop → finally → `PlaybackFinished`, плюс логирование)
  попадал в `LogService.AddLog`, который писал в коллекцию через **синхронный**
  `Dispatcher.Invoke`. UI занят `Wait()` — помп не может завершиться — UI не может
  отпуститься. После конца видео `Stop()` выходит по `!IsPlaying` сразу — поэтому «нормально».

**Исправлено**:
- `LogService` — больше никогда не ждёт UI из фона: на UI-потоке пишет инлайн,
  из фонового — `BeginInvoke` (fire-and-forget). `lock` убран за ненадобностью
  (коллекция мутируется только на UI).
- `FramePump.Stop()` — только Cancel + сброс паузы + смена флага; **никаких Wait на UI**.
- Передача capture следующему прогону перенесена в `Play()`: новый прогон дожидается
  старого на фоновом потоке (`prev?.Wait(3000)` внутри `Task.Run`) — гонки двух циклов
  на одном `FileSourceService` нет, но и UI никто не блокирует.
- `Stop()` на паузе теперь мгновенен: `_isPaused` сбрасывается в Stop, спящий паузный
  цикл будится отменой токена и выходит за ≤100 мс.

**Проверено здесь**: build 0 ошибок; тесты 28/28 PASS.

## Обновление 11: починенный экспорт видео, точные контуры, терминальный комбобокс

**«Экспортированное видео не открывается (файл повреждён)»**
- Причина №1: `VideoWriter` создавался с размером из свойств потока — у многих кодеков он
  расходится с фактическими пикселями, и MP4-контейнер получается «битым». Теперь размер
  берётся из **первого реально записанного кадра**.
- Причина №2: первым пробовался `avc1` (H.264); в сборке OpenCV без H.264-энкодера writer
  «открывался», но не писал ничего — на выходе пустой контейнер. Порядок кодеков:
  **`mp4v` (гарантированный) → `avc1` (если доступен)**; для .avi — MJPG. Выбранный кодек
  пишется в лог.
- Дополнительно: если ни один кадр не записан — файл удаляется, в логе ошибка (не оставляем
  «битых» mp4); крошечный результат (<4 КБ) — предупреждение «попробуйте AVI/MJPG».

**Контуры/маски «съезжали» с объектов**
- В конвейере маски `Resize`/`ConvertTo` вызывались «в себя» со сменой размера/типа —
  OpenCV это не определяет as error в release, а данные портятся (маска уезжала).
  Цепочка переписана на отдельные Mat: 160² float → resize → 640² → threshold 255 →
  ConvertTo в byte → WarpAffine в координаты кадра (анлиттербокс). Контур теперь ложится
  на объект.

**Highlight-комбобокс — терминальный стиль**

## Обновление 12: контуры больше не уезжают (неквадратный вход seg-модели)

**Симптом**: боксы точные, а контур/маска смещены вниз и вытянуты; чем ниже объект в кадре —
сильнее съезд (видно на примере с вертикальным видео).

**Настоящая причина**: скачанная seg-модель имеет **фиксированный неквадратный вход 640×480**
(выходы 1×116×6300 и proto 1×32×120×160), а конвейер маски пересобирал proto-маску в
**квадрат** `netW×netW`. По вертикали это растягивает содержимое в 640/480 ≈ 1.33 раза
относительно верхней кромки — отсюда «хвосты» вниз. Для квадратной модели 640×640 баг
невидим, поэтому тесты его не ловили.

**Исправление** (Services/DetectorService.cs, AttachMaskPolygons):
- resize маски теперь идёт в **реальный размер входа**: `Size(_netW, _netH)`, а не квадрат;
- кроп-прямоугольник бокса в net-пространстве клампится по высоте к `_netH` (было `_netW`);
- страховка: если proto не делится на вход ровно — размер доводится до кратного.

**Проверено числово** (реплика конвейера на python+ONNX, кадр 810×1080, та же модель):
смещение маски относительно бокса было dy=+69…+134 px (IoU 0.38–0.47), стало dy≈±8 px,
IoU **0.92–0.97**. Контур садится на силуэт.


## Обновление 13: выбор объектов кликом («🎯») — подсветка и трек только выбранных

**Что это**: кнопка-переключатель «🎯» в строке Highlight. Включённый режим — клик по
объекту на превью **выбирает** его: с этого момента боксы/контуры/маски рисуются только
на выбранных (и в воспроизведении, и в экспорте видео). Счётчик «sel:N» справа от кнопки.

**Управление**:
- клик — выбрать объект (повторный клик по тому же — снять);
- Ctrl+клик — добавить/убрать из выбора (мультивыбор нескольких объектов);
- клик по пустому месту — очистить; Esc — очистить всегда;
- переключение источника — выбор сбрасывается автоматически.

**Как это работает**:
- хит-тест: сначала по полигону instance-маски (точное попадание «в объект», а не в рамку),
  если масок нет — по боксу; при наложениях выигрывает меньший объект;
- «захват на ходу»: выбор живёт как {класс + бокс + последний TrackId}. На каждом кадре
  чистая логика `SelectionLogic.Apply` переставляет флаг IsSelected: совпавший TrackId
  — сильнейший признак, иначе IoU≥0.3 того же класса. Так объект переживает короткие
  перекрытия и не «перескакивает» на чужой класс;
- экспорт видео получает снапшот выбора (класс+бокс) и делает тот же ре-захват с первого
  кадра — трекер экспорта живёт отдельно от превьюного, поэтому сопоставление по геометрии;
- логика выбора (`Services/SelectionLogic.cs`) — чистая и без OpenCV/WPF: point-in-polygon,
  IoU, toggle-семантика, ре-захват — покрыта 17 новыми тестами (было 31, стало 48).
- клики не мешают зуму/панораме: движение мыши >4px по-прежнему панорамирует, клик без
  сдвига — выбирает. На паузе и для фото кадр перерисовывается мгновенно.

**Ограничение**: это SORT + геометрический ре-захват, без re-ID по внешности:
объект, надолго спрятавшийся и уехавший далеко, может не быть подобран. Это следующий
шаг, если понадобится.

**Проверено**: build 0 ошибок; тесты 48/48 PASS.
